### Stage 1: schema and synthetic data

| Date | Decision | Reason |
|---|---|---|
| 2026-10-10 | **Python decides every structured fact** (category, brand/model, specs, condition, price, currency, location, language, near-duplicate links) from a seeded catalog (`data/generator/`). The writer (template or Gemini) only writes title + description, from those facts. | Ground truth for the Stage 3 eval comes from the generator, not from LLM output, so it is reliable. The same seed always gives the same facts. |
| 2026-10-10 | Gemini text is **validated** before use: right language, length limits, and **no written prices** (regex). A rejected item keeps its template text and is retried at most twice. | The structured price is the only source of truth for prices (spec section 4). |
| 2026-10-10 | Schema deviations from spec section 6: added `source` + `external_id` (unique together; makes loading idempotent), `price_qar`, `language`, `updated_at`. The btree price index is on **`price_qar`** rather than `price`. | Filters compare normalized prices. Upserts need a stable key. |
| 2026-10-10 | `id` is `bigint` identity (not uuid). | The LLM will cite listing IDs in Stage 7; short integers cost fewer tokens and are harder to garble. |
| 2026-10-10 | `fts` = `to_tsvector('english', search_text) \|\| to_tsvector('arabic', search_text)`. | Supabase Postgres 17 ships an `arabic` text-search config (checked with `pg_ts_config`). Listings mix both languages. Revisit in Stage 5. |
| 2026-10-10 | HNSW index on `embedding` is **deferred to Stage 2** (created after embeddings load). | Spec Stage 2: "build HNSW index after loading". |
| 2026-10-10 | Row Level Security enabled on `listings` and `schema_migrations`, with no policies. | The Supabase Data API (anon key) cannot read or write them. The backend's `postgres` role bypasses RLS. |
| 2026-10-10 | When `search_text` changes on upsert, `embedding` is reset to null. | Stage 2's resumable job re-embeds exactly the changed rows. |
| 2026-10-10 | `image_url` is null for synthetic listings. | No real photos. Random stock photos would mislead. Stage 9 renders a category placeholder. |
| 2026-10-10 | Catalog stops at models released in 2025. | 2026 launches were not verified. |
| 2026-10-10 | Gemini is called through the **Interactions API** (`client.aio.interactions.create`, `response_format` JSON schema, `thinking_level="low"`, `store=False`). | Current docs (structured-output, thinking pages, 2026-10-10) document this API. `gemini-3.8-flash` supports thinking levels low/medium/high (default medium). |
| 2026-10-10 | Generator pacing: 4 requests/min, 50 listings per request. Daily-quota 429s stop the run cleanly, and progress is cached in `data/cache/`. | Free tier for `gemini-3.8-flash` on this project: **5 RPM, 20 RPD** (user read from AI Studio, 2026-10-10). |

### Stage 2: embeddings and ingestion

| Date | Decision | Reason |
|---|---|---|
| 2026-10-11 | `EmbeddingProvider` interface (`embed_documents(texts, titles)`, `embed_query(text)`) with `GeminiEmbeddingProvider` as the first implementation, chosen by `EMBEDDING_PROVIDER`. | Spec section 5: swappable providers. |
| 2026-10-11 | Documents are embedded as `title: {title} \| text: {search_text}` and queries as `task: search result \| query: {text}`. | Google's recommended asymmetric-retrieval prefixes for `gemini-embedding-2` (no `task_type`). |
| 2026-10-11 | Each text is sent as its **own `Content`**. | A plain list of strings is folded by the SDK into one Content, which `gemini-embedding-2` turns into one aggregated embedding (checked in SDK source and docs; covered by a unit test). |
| 2026-10-11 | The job is **paced per text**, not per call: at most 90 texts and 27k estimated tokens per minute (90% of the limits), 45 texts per call. The daily budget is `RPD − 100 reserved for search queries − texts already sent today` (Pacific day, from `docs/logs/embedding-runs.jsonl`). | Measured: one call with 60 texts followed by a second with 60 hit the 100 RPM limit, so each text counts as a request. 2,205 listings therefore take 3 free-tier days. |
| 2026-10-11 | Tokens are **estimated** as characters ÷ 2.5. | The embed response has no usage metadata on the Gemini API. `count_tokens` on sampled listings gave about 3.0 characters per token (English 3.04, Arabic 2.81, mixed 2.97), so ÷ 2.5 overestimates slightly, which keeps pacing safe and costs conservative. |
| 2026-10-11 | Pending = `embedding is null or embedding_model <> EMBEDDING_MODEL`. Vectors are written per batch, and only if `md5(search_text)` still matches what was embedded. | Resumable and re-runnable (no-op when nothing is pending). Changing the model re-embeds everything; a concurrent reload never leaves a stale vector. |
| 2026-10-11 | The dimension lives in the column type (`vector(1536)`); the job refuses to run if `EMBEDDING_DIMENSION` differs. | Spec: model name and dimension stored in config and in the database. |
| 2026-10-11 | Gemini-written synthetic listings are embedded first. | Template-text rows will change after the next `rewrite`, so embedding them early would waste free-tier requests. |
| 2026-10-11 | HNSW index (`vector_cosine_ops`, default `m=16`, `ef_construction=64`) is created by the embed job once no rows are pending, followed by `ANALYZE`. Queries set `hnsw.iterative_scan = relaxed_order` so filtered searches still return enough rows. | Spec: build the index after loading. pgvector 0.8 iterative scans fix the "filter after ANN" recall drop. |
| 2026-10-12 | `with_retries` is the **only real retry layer**. It also retries google-genai's wrapped `APIConnectionError`/`APITimeoutError` (found by class name and `raise ... from` cause chain). The Interactions client is created with `HttpRetryOptions(attempts=1)` (the SDK minimum, 1 internal retry), and every attempt has a hard `asyncio.wait_for` deadline. | On 2026-10-12 a dropped connection crashed the rewrite (the wrapper class was not recognized), and a later batch hung for 15+ minutes because the SDK's default 3 internal retries × 240 s timeout ran inside each of our 6 attempts. The embeddings client (classic `models` API) has no SDK retries by default. |

### Stage 3: evaluation harness and baseline

| Date | Decision | Reason |
|---|---|---|
| 2026-10-13 | **Relevance comes from structured facts**, not text: each query has a `relevant` spec (category, models, conditions, price, sale/rent, location, attributes) evaluated against `data/listings.jsonl` by `eval/ground_truth.py`. | Spec: derive ground truth from the generator's metadata. The answers do not depend on how messy the text is, or on later Gemini rewrites (which change text only). |
| 2026-10-13 | Vague phrases have a written mapping (`eval/README.md`): "great condition" = like_new/good, "around X" = ±15%, "low mileage" = ≤ 50,000 km, monthly rent compares yearly ÷ 12, and so on. | Spec section 7 asks for documented mappings. Stage 4 must use the same ones, or the eval would measure disagreement about words rather than retrieval. |
| 2026-10-13 | 45 queries: 29 English, 12 Arabic, 4 mixed; all 6 categories; tags for price, condition, attribute, model, rent/sale, location and vague intent. Frozen before the first baseline run. `ph05` (no brand-new Pixel 10 Pro exists) and `fu02` (no good L-shaped sofa under 1,500 QAR) were changed *before* that run because their answer sets were empty. | An empty answer set cannot be scored. No query was changed after seeing any retrieval result. |
| 2026-10-13 | Recall@10 uses `min(relevant, 10)` as the denominator. A **"wrong in top 10"** share (results breaking at least one constraint) is reported alongside it. | Without the cap, a query with 40 right answers could never exceed 0.25. Without the wrong-share, queries with 2 right answers look perfect while 8 of 10 results are wrong. |
| 2026-10-13 | Eval results are keyed by `external_id`, not the database `id`. | Stable across reloads and databases. |
| 2026-10-13 | `eval/run.py` runs the FastAPI app **in-process** (httpx `ASGITransport` + the app lifespan) by default, or a live server with `--url`. | One command, same code path as production, no server to start. |
| 2026-10-13 | `POST /api/search` rejects unknown fields (`extra="forbid"`), including `filters`, until Stage 4. Errors: 422 bad input, 503 not configured, 429 embedding quota exhausted, 502 upstream failure (details logged, not returned). | A filter the API silently ignores would look like a working filter. |
| 2026-10-13 | Query embeddings are cached in `query_embedding_cache` (migration 002), keyed by sha256 of model, dimension and the exact model input. The query is only whitespace-normalized; case and wording are kept. | Every free-tier embedding counts against 1,000/day; the cache makes eval re-runs free and exactly reproducible. Lowercasing could change meaning ("US" vs "us"). |
| 2026-10-13 | Latency: one database round trip per search when `limit ≤ 20` (no `SET` needed, since pgvector's default `ef_search` 40 ≥ 2 × limit), and a cached search uses a single pooled connection for lookup + search. Cache misses release the connection during the embedding call. | Each round trip to Supabase from the dev machine is about 313 ms. Supavisor ignores `server_settings` sent at connect (tested: `hnsw.ef_search` stayed 40). Cached latency went from 1,507 ms to about 850 ms with identical scores. |
| 2026-10-13 | Fixed a Stage 1 template bug: mixed-language rental titles could end in "للبيع" ("for sale"). 9 listings were rewritten (facts unchanged), re-embedded, and covered by a regression test. The baseline was recorded after the fix. | Found while reading baseline failures. The rent list has the same length as the sale list, so every other listing's text is byte-identical. |

### Stage 4: query understanding

| Date | Decision | Reason |
|---|---|---|
| 2026-10-13 | Extraction model **`gemini-3.5-flash-lite`** (`EXTRACTION_MODEL`), thinking level `minimal`. | User-confirmed. Free tier 15 RPM / 500 RPD vs 20 RPD for `gemini-3.8-flash`; an eval run alone is 45 calls. |
| 2026-10-13 | **The LLM labels, Python decides.** The model fills a fixed form (`QueryParse`: condition *intent* such as "great", price comparator + amount + currency + period, ...). `parse_to_filters` maps it to SQL filters with the same rules as `eval/README.md` ("great" = like_new/good, "around" = ±15%, "low mileage" = ≤ 50,000 km, rent per month unless stated). | One written definition of every vague phrase, shared by the system and the eval. Mapping changes never need a new LLM call. |
| 2026-10-13 | Allowed values come from the database (`Catalog`: 6 categories, 45 brands, 80 models, 16 furniture types, 7 property types, 22 locations) and are `enum`s in the response schema. Values outside the catalog are dropped again in code. | The LLM can only name things a filter can match ("G63" → "G 63 AMG", "لوسيل" → "Lusail"). |
| 2026-10-13 | The schema has **no `maxItems` / `additionalProperties`**; list limits are enforced in code. Optional fields are left out rather than sent as null. | The structured-output docs list both keywords, but the API returned HTTP 400 for a schema using them (bisected 2026-10-13: without them the same schema works). |
| 2026-10-13 | Schema deviations from spec section 7: `brands[]` and `models[]` (lists, not single values), `attributes{}` with explicit operators (`eq`, `any_of`, `min`, `max`, `contains`) on a whitelist of keys, `price_period` for rent comparisons. A property price with no "rent"/"sale" word is a sale from 200,000 QAR, otherwise a monthly rent. | Product lines span several catalog models ("MacBook Air"), and "android" spans brands. The whitelist keeps arbitrary JSON keys out of SQL. The 200k rule stops "villa under 2 million" from matching every rental. |
| 2026-10-13 | Filters are SQL `WHERE` clauses (all values bound as parameters) inside the vector query. Every pooled connection sets `hnsw.iterative_scan = strict_order` on open and on reset (same round trip as asyncpg's `RESET ALL`), so a selective filter still returns up to `limit` rows in exact order. | A role-level default would also change other users of the database (the permission check blocked it, rightly); Supavisor ignores settings sent at connect. Checked: SQL row counts for 6 filters match a Python computation over the dataset exactly. |
| 2026-10-13 | **Guards against invented fields** (`app/retrieval/guards.py`): fields only count for categories where they mean something; models and property types must belong to the extracted category; number filters must appear in the query (digits, "40k", "1TB", "30 الف", number words like "غرفتين"); an English location must be named in an English query; invalid values drop one field, not the whole extraction. | Found in the first Stage 4 run: flash-lite filled fields the query never mentioned, often with example values from its instructions ("studio for rent" got storage_gb = 512; "office chair with delivery" got location = Lusail and year ≥ 2020). 7 of 45 pages came back empty. These rules are generic, not tuned to eval queries. |
| 2026-10-13 | Extraction never fails a search. On error, timeout (`EXTRACTION_TIMEOUT_S`, default 20 s) or quota, search runs unfiltered and `debug.extraction.error` says why. Interactive calls get one retry. Failures are not cached; results are cached in `query_extraction_cache` (migration 003) keyed by model, a hash of prompt + schema + catalog, and the query. | Spec: fall back to unfiltered search. On 2026-10-13 flash-lite was overloaded (503 "high demand", 21–233 s per call), so the fallback path was exercised for real. |
| 2026-10-13 | `POST /api/search` accepts explicit `filters` (validated, unknown fields rejected) which replace extraction, and `extract: false` to reproduce the Stage 3 baseline. | The UI's editable filter chips (Stage 9) need explicit filters; `extract: false` keeps the baseline reproducible from the same code path. |
| 2026-10-14 | **Extraction calls `generateContent`** (`response_json_schema`), not the Interactions API. `GeminiJsonClient(api=...)` supports both; the Stage 1 generator stays on Interactions. | Side by side on 2026-10-14, the same model, prompt and 27-field schema gave mislabelled fields through Interactions ("2 bedroom" → `storage_gb = 2`, "2020 or newer" → price under 2020, "GCC specs" → `property_type = villa`) and correct ones through generateContent (`bedrooms = 2`, `min_year = 2020`, `gcc_specs = true`). With a 3-field schema, Interactions was right only when properties were defined in alphabetical order. Eval: Recall@10 0.834 → 0.996. |
| 2026-10-14 | Every schema field has a one-line `description` (`FIELD_DOCS` in `app/providers/llm.py`); the prompt says most queries need two to four fields and examples must not be copied. | Generic guidance added after the first runs; neither the thinking level (`minimal` vs `low`, A/B on 8 queries) nor the field descriptions alone fixed the mislabelling, which was the API. |
| 2026-10-14 | Guards also require units: storage/RAM need GB/TB (and storage ≥ 32 GB), areas need sqm/متر, mileage needs km. Arabic place names are checked against a small gazetteer (`PLACE_NAMES_AR`). Two **backstops** fill a field only if the LLM left it empty: an explicit price limit ("under N", "أقل من N", with currency and per-month/per-year) when the number has no other unit, and a bedroom count ("2BR", "N غرف", "غرفتين"). Every drop or fill is listed in `debug.extraction.guard_notes`. | The model put "under 15000 a month" into area, mileage, storage and RAM but not price, "Dell XPS 13" into storage = 13, and missed "غرفتين". The rules are generic; on 10 unseen queries (unscored, `docs/results.md`) the price backstop fired 3 times and 9 of 10 extractions were fully correct. |
| 2026-10-14 | `EXTRACTION_MAX_ATTEMPTS` (default 2) is configurable; `eval/run.py` has `--concurrency`, `--extraction-timeout` and `--extraction-attempts` for filling the cache, and `--no-extract` for the baseline. | On the overloaded free tier, interactive search should give up quickly (and search unfiltered), while a one-off eval fill can wait. 503 retries count against the daily quota, so retries are kept low. |

### Stage 5: hybrid retrieval

| Date | Decision | Reason |
|---|---|---|
| 2026-10-14 | **Hybrid is the default** (`RETRIEVAL_MODE=hybrid`): top 50 by vector distance + top 50 by `ts_rank` on `fts`, both under the same filters, in **one SQL round trip**; fused in Python with **RRF, k = 60** (`app/retrieval/rrf.py`). `retrieval: "vector"` on a request, or `--retrieval vector` in the eval, reproduces Stage 4. | Spec Stage 5. k = 60 is the standard value from Cormack et al. (SIGIR 2009). RRF uses ranks only, because cosine similarity (~0.8) and ts_rank (~0.05) are on unrelated scales. Latency is unchanged (EXPLAIN: HNSW index scan + GIN bitmap scan). |
| 2026-10-14 | The full-text query is the query's lexemes under **both** the `english` and `arabic` configs, **OR-ed** (`'samsung' \| 's24' \| '512gb'`). | `plainto_tsquery` ANDs every word, so natural sentences ("used iPhone 15 Pro under 3000") match almost nothing. Both configs, because `fts` is english ∥ arabic and queries mix languages. |
| 2026-10-14 | The full-text side searches the **LLM's extracted `keywords`** (`HYBRID_KEYWORDS=llm`), not the raw query. With no keywords it is skipped (pure vector order). Keyword-score ties are broken by vector similarity (in SQL and in Python), not by id. | Measured on the eval: raw-query full-text 0.987 (regressions on `ph06`, `car08`) vs 0.996 with keywords; without filters raw-query hybrid falls to 0.689 vs 0.853 for vector alone. `ts_rank` has no IDF, so common words ("used", "في", "سيارة") dominate, and words the filters already enforce get matched twice. `HYBRID_KEYWORDS=query` keeps the other option. |
| 2026-10-14 | Third backstop: `listing_type` from an explicit "for sale" / "for rent" / "للبيع" / "للإيجار" (only if exactly one appears, property categories only, only when the LLM left it empty). | Hybrid exposed a hidden Stage 4 miss: "townhouse for sale" had no `listing_type`, and full-text on "townhouse" promoted rentals. Vector order had hidden it. |
| 2026-10-14 | Results carry `ranks` (`{"vector": 3, "keyword": 1}`) and the RRF `score`; debug shows `candidates` per side. | Lets the UI and the eval see why a listing is where it is. |

### Stage 6: reranking

| Date | Decision | Reason |
|---|---|---|
| 2026-10-15 | **Reranker: Gemini listwise** (`GeminiListwiseReranker`, `gemini-3.5-flash-lite` via `generateContent`, thinking `minimal`), behind a `Reranker` interface (`rerank(query, candidates, top_n)`). | User-chosen (option A of: Gemini listwise / hosted rerank API / local model). No new account; reads Arabic; local models are ruled out by the spec for free hosting. A hosted rerank API remains a drop-in through the interface. |
| 2026-10-15 | Rerank the top **50** retrieval candidates (`RERANK_CANDIDATES`) into the top **10** (`RERANK_TOP_N`). Candidates are numbered lines (title, structured facts, price with rent period, first 160 characters of the description); the model returns numbers only. | Spec: top ~50 to top ~10. Numbers instead of listing ids keep the output short and impossible to garble into another listing. Mean 2,626 input tokens (max 8,257) per call. |
| 2026-10-15 | **The reranker can only reorder** (`apply_ranking`): out-of-range or repeated numbers are dropped (and counted), and unranked candidates keep their retrieval order after the ranked ones. On any error, timeout or quota, the retrieval order is kept and `debug.rerank.error` says why. One candidate: no call. | Same rule as the spec's ID validation for answers: the LLM can never add a listing or undo a filter. Search never fails because of the reranker. |
| 2026-10-15 | Rerank results are cached in `rerank_cache` (migration 004), keyed by model, prompt hash, and sha256 of the query + `top_n` + every candidate's id **and text**. | Eval re-runs cost nothing; a changed listing text never reuses a stale order. |
| 2026-10-15 | Extraction and reranking **share one rate limiter** per Gemini model (`llm_limiter` in `app/main.py`). | They draw from the same 15 RPM / 500 RPD free quota; separate limiters would together exceed it. |
| 2026-10-15 | **On by default** (`RERANK_ENABLED=true`); `rerank: false` per request, or `--no-rerank` in the eval, reproduces Stage 5. | Eval: Recall@10 0.996 → 1.000 (fixed `lp03`, the only vague-intent failure), at about 3× the cost per new query and +7.3 s on a cache miss. Caching hides the cost for repeated queries. Hand checks found it ignores "cheap" and slightly reduces variety (`docs/results.md`), so a price-sort hint and a per-model diversity cap are noted as follow-ups. |

### Stage 7: grounded answers and chat

| Date | Decision | Reason |
|---|---|---|
| 2026-10-15 | `LLMProvider.generate_answer(query, listings)` on the same Flash-Lite provider, client and rate limiter as extraction (`generateContent`, JSON schema `{summary, recommended[]}`). | Spec section 5 interface. One model and one limiter for the shared 500/day quota. |
| 2026-10-15 | **The answer model never sees price numbers**, only `price rank k of N (1 = cheapest)`. | Removes the temptation at the source: it can say "the cheapest" with nothing to copy. On the 45-query check, 0 sentences had to be removed. |
| 2026-10-15 | **Grounding in code** (`app/answers/grounding.py`): citations are 1-based numbers mapped to ids, out-of-range or repeated ones dropped, at most 3; any sentence with a price (currency amounts, "priced at", grouped numbers without a unit, "40k"), link, e-mail or phone number is removed; template fallback if nothing is left. | Spec acceptance: no response contains a price or link that did not come from the database. Numbers with units (512GB, 45,000 km, 4K screen) are kept. |
| 2026-10-15 | **Generate in full, ground, then stream** the checked text as `token` events. `filters` is sent as soon as extraction is done; `listings` before any text. | Streaming raw model tokens would let a price reach the client before the check. Costs the time to the first token (the answer call, ≈ 5 s), not total time. |
| 2026-10-15 | Cards are **re-read from Postgres by id** (`hydrate`) right before the `listings` event, not taken from LLM output or from earlier pipeline objects. | "Hydrate listing data from the DB" (spec section 4). The grounding check also re-reads every card's title, price and currency independently. |
| 2026-10-15 | **No matches:** no LLM call. Each applied filter (except category) is dropped once and matches are counted in **one SQL query** (`count(*) filter (where ...)` per variant). The reply names up to two relaxations with real counts, in English or Arabic. | "Handle no good matches honestly (suggest relaxing a constraint)." A count from the database cannot be wrong the way an LLM suggestion can. |
| 2026-10-15 | The reply language is chosen in code (more Arabic than Latin letters → Arabic) and given in the prompt. | In the first smoke test the model answered an Arabic query in English despite "use the language of the query". 45 of 45 matched afterwards. |
| 2026-10-15 | Answers are cached in `answer_cache` (migration 005) as raw model output, keyed by the query and every listing's id and text as the model saw them. | Re-runs are free, and changes to the grounding rules still apply to cached answers. |
| 2026-10-15 | `ChatRequest` = `{session_id, message}` (`session_id` accepted, unused until Stage 8). An `error` event is added for an unavailable search; `done` always follows. | Spec section 7 contract. Clients can rely on `done` closing every stream. |

### Stage 8: conversation state

| Date | Decision | Reason |
|---|---|---|
| 2026-10-15 | **Delta extraction + deterministic merge.** The LLM reads only the new message (same prompt and cache as single-turn); `app/conversation/merge.py` combines the delta with the saved filters by fixed rules (replace per field, attributes per key, keywords combined, brand switch drops other brands' models, new category starts over). `extract_filters(query, state)` keeps its `state` parameter but the chat does not pass it. | (1) The extraction cache stays correct: a message's delta means the same in every conversation, so no context has to be in the cache key. (2) Merges are unit-testable and predictable. (3) Stage 4 showed the small model is unreliable at reproducing structured state. |
| 2026-10-15 | A follow-up without a category gets the conversation's category **before the guards run** (`QueryUnderstanding.with_context`). | Otherwise the scoping guard drops "for rent" or "غرفتين" as "not for unknown category". The cached parse itself stays context-free. |
| 2026-10-15 | **"Cheaper" = comparable price (QAR, yearly rent / 12) ≤ median − 0.001** of everything matching the previous filters, computed with `percentile_cont(0.5)` in SQL. An explicit price in the same message wins. | The median of the full previous match set, not of the 10 cards shown, so the rule does not depend on how the page was cut, and it matches the eval's definition. Prices have 2 decimals, so "≤ median − 0.001" means "< median". |
| 2026-10-15 | "Start over" / "new search" / "ابدأ من جديد" are detected by a rule **only at the start of a message**; the rest of the message (if any) becomes a new search.
